## 2. Synthetic evaluation corpus

`python -m scripts.build_sample_documents` writes 13 fictional documents, plus `expected.json` with ground truth for document type, each field's status and normalized value, and 10 readiness scenarios with per-requirement expected statuses. `python -m scripts.evaluate_documents` runs the real validation, extraction, classification and rule code on them.

| Category | Documents |
|---|---|
| Text-layer forms | complete, incomplete, conflicting, injection (MRI); PT request form |
| Supporting documents | 3 referral letters (one late), 1 clinical note summary |
| Unrecognized | 1 general letter |
| Needs OCR | scanned PNG, image-only PDF, mixed PDF (page 2 scanned) |

**Limits of this corpus:**
- It is small.
- It was generated by the same project that wrote the extractor, using the same label wording, so high scores show the pipeline behaves as specified on its own format. They are not evidence of accuracy on real or varied documents.
- There is no handwriting, no tables, no multi-column layout, and no noisy scans.

## 6. Known limitations

- The extractor targets the synthetic labeled-form format. Other layouts will mostly yield `ABSENT` or `UNRECOGNIZED` (and therefore manual review), not wrong values.
- OCR and confidence thresholds are provisional and uncalibrated.
- Items needed for later phases:
  - case linking (`review_state`) and agent access are Phase 7;
  - the retention cleanup job and malware scanning are open (Phase 7/8);
  - users can't correct extracted values yet.
- Single-process background jobs. Interrupted jobs are closed on the next analyze request, not at startup.
